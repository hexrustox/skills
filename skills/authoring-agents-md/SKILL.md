# AGENTS.md

`AGENTS.md` is the always-loaded instruction file for agents working in a repo. It earns its place only when it changes behavior the model would otherwise get wrong. The ASDLC specification is distilled in [references/authoring.md](references/authoring.md).

## Scope

This skill edits `AGENTS.md` files only. Leave every other instruction file untouched.

## Instructions

### 1. Choose the mode and targets

Find the repository root. If the session starts below it, use the workspace root or `git rev-parse --show-toplevel`.

**Create** applies when the user asks to create, write, add a new file, or initialize:

- Target `<root>/AGENTS.md`.
- When the user names a directory, target `<dir>/AGENTS.md`; when they name a file, target that file.
- Create only the new AGENTS.md files the user names. A request for the root does not authorize nested files.
- If a target already exists, treat it as an update limited to that file; do not widen the search.

**Update** applies when the user asks to update, audit, review, edit, revise, clean up, or refresh:

- Glob `**/AGENTS.md` from the repository root and include every match, including the root and every nested file. Treat an audit request as an update.
- If the user names a file or directory, glob first, then narrow the matches to that scope.
- If no file matches, report that and suggest creating one; do not create it unasked.

If the request is ambiguous, use Create when no target exists and Update when AGENTS.md files already exist; state the choice.

Skip matches under dependency, vendor, generated, build, and version-control directories. Done when the mode, every target path, and whether each target is new or existing is explicit.

### 2. Harvest evidence

Read the repository before drafting. Relevant sources include the README, manifests and workspace configs, task runners, CI workflows, scripts, formatter/linter/type-checker configs, environment examples, ADRs, glossaries, and the source layout. Read every existing in-scope AGENTS.md in full.

For each candidate line, name its source: a command the agent cannot guess, a non-default convention, an architectural constraint, a gotcha, or a decision from the user. Cut any line without a source. Treat content generated by an init command as a lead to verify, not as truth.

Do not restate what a config, script, or the directory layout already owns. Point to the command or authority instead. Ask the user only for mission, core constraints, permissions, or judgment boundaries the repository cannot answer.

Done when every candidate line has a source and every toolchain-owned fact is marked to stay out of AGENTS.md.

### 3. Draft or update the files

**Create.** Read [references/authoring.md](references/authoring.md) and start from [assets/AGENTS.md.template.md](assets/AGENTS.md.template.md). Keep only sections with real content: Mission, Toolchain, Judgment Boundaries, Skills roster, and an optional Context Map. Omit empty sections and placeholder filler.

**Update.** Read [references/authoring.md](references/authoring.md) and [references/update.md](references/update.md). Audit every line, rewrite what survives, and remove what does not. Apply every change supported by evidence.

**Root and nested files.** The root owns cross-cutting mission, repo-wide commands, verification, global boundaries, and the skills roster. A nested file owns package- or service-specific commands, conventions, and gotchas. A nested rule may refine the root for its subtree; it must not contradict a root rule that still applies. Keep each meaning in one place. Move branch-specific detail only into an in-scope nested file or an existing doc; do not create new docs.

Done when every surviving line traces to evidence, every rule is concrete enough to follow and work rules say what done means, each meaning has one home, and no empty sections remain.

### 4. Write and verify

Write only the target `AGENTS.md` files. If a root/nested conflict or an unanswered judgment decision would change the content, stop and ask before writing that part.

Verify the final files:

- Every project-specific command exists in a manifest, task runner, script, or CI workflow.
- Every referenced path, doc, and skill definition resolves.
- No meaning is duplicated across the root and nested files, and no rule contradicts another.
- The root stays small enough to load every turn; keep it to roughly 200 lines or 5,000 tokens.
- Every rule is concrete enough to follow and check.

Re-read each file line by line against the standard before finishing. Report the files changed, the removals, and any unresolved split or conflict. Done when the targets are written and every check passes or its gap is reported.
